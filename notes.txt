12. A KRaft broker needs more than local storage initialization to become operational. During startup, it must register with the KRaft controller quorum and catch up with the cluster metadata. If the controller quorum is unavailable, the broker cannot complete startup and its broker listener is eventually shut down. Once the quorum becomes available, the broker can register, synchronize metadata, and become available to producers/consumers.

An already-operational broker can continue serving certain existing data-plane operations even when the controller quorum becomes unavailable, because it already has the necessary partition/leader information locally.

13. There is a chance that duplicate messages are logged in kafka logs. What might happen is, assume there is a event(E1) and it has a message (ABC), now ABC is in kafka log file at offset 1. The broker send back ack to producer but the ack fails. Now broker will hit a retry if it didn't get the ack. Hence the same event(E1) is send again and now the broker again appends the same message in logs, so eventually we have
Broker-1.logs:
E1 : offset 1
E1 : offset 2

14. There is also a message re-ordering condition that might happen in kafka. When we enable these settings : max.in.flight.requests.per.connection = N and retry > 0. For now, assume these batches have 1 event in them. What might happen is, assume there are multiple partition of record accumulator(batch-1, batch-2) which is being written in socket. Now assume batch-1 failed due to some issue but batch-2 succeeded(broker appended all events in logs files).
Broker-1.logs:
E2 : offset 1
Now if the retry is configured and ack is not received then, the batch-1 will be again send from producer to broker. Now the overall ordering would be all events of batch-2 followed by all events of batch-1.
Broker-1.logs:
E2 : offset 1 (might be related to order-payment)
E1 : offset 2 (might be related to order-creation)
This happens as broker has no way to identify if the events they are getting are in order. The solution is to set : spring.kafka.producer.properties.enable.idempotence = true in producer

15. What happens when spring.kafka.producer.properties.enable.idempotence=true is true?
Sender End:
In producer, for each topic+partition a different batch is created in record-accumulator. Now when we enable this key, each producer gets a unique ID, this is the producerId(not stored anywhere). Now in each batch apart from events 3 additional details are added - PID, BaseSequence(the start sequence number of batch), LastSequence(The last number showing total events inserted till date).
Receiver End:
        Batch-1
        Topic-A
        Partition-0
        PID:1001
        BaseSequence:0 (meaning this is the 1st batch)
        LastSequence:2
        [E1:seq0, E2:seq1, E3:seq2] (created at producer's end)
When the batch is received, broker checks in it's in-memory map the next sequence for a given [topic+partition+PID] what is the next sequence it is expecting, and it matches with the BaseSequence. So the 2nd time this batch will be received, it will be as below:
        Batch-2
        Topic-A
        Partition-0
        PID:1001
        BaseSequence:3 (meaning this is not the 1st batch)
        LastSequence:4
        [E4:seq3, E5:seq4]
If this is the case, then only batch is accepted. But if a producer re-starts, it will get a new ProducerId. Assume a case where ack was not received for a batch(the batch is already in logs). Also assume as soon as producer was trying to send the batch again, it crashed. The producer restart and a new producerId is assigned to it. Now this time the batch will be sent with almost all same data except PID and kafka will accept it a and write it in logs, even though they are duplicate events.
