Problem: DUAL WRITE

Assume we have a method as below:

    @PostMapping("/api/orders")
    public ResponseEntity<String> createOrder(@RequestBody Order order) {
        // step 1
        orderRepository.save(order);
        // step 2
        kafkaTemplate.send("order-events", order.getOrderId(), order);
        return ResponseEntity.ok("order-created");
    }

Issue:
DB and Kafka are two independent systems. If one write succeeds and the other fails, the system can end up in an inconsistent state. Both writes are not atomic by default.

Solution:
1. @Transactional + Manual Exception Throw

    @Transactional
    public void createOrder(OrderRequest request) {
        orderRepository.save(order);
        try {
            kafkaTemplate.send("order-events", event).get();
        } catch (Exception e) {
            throw new RuntimeException("Kafka failed, rolling back DB transaction", e);
        }
    }

Assume the DB write succeeds, but the Kafka record is stored and its acknowledgment is lost due to a network issue. The producer receives an exception, and the DB transaction rolls back. The result is that the record may exist in Kafka but not in the DB. This approach does not guarantee atomicity across DB and Kafka.

2. Two-Phase Commit (2PC)

For 2PC to work, all participants must support the protocol and participate in the same distributed transaction. A typical database transaction and Kafka transaction are not automatically coordinated by the code above. Therefore, @Transactional + KafkaTemplate.send() does not provide 2PC.

3. Outbox Pattern

Write the business data and an event record to the same database in a single DB transaction. A separate process reads the outbox and publishes events to Kafka.

    @Transactional
    public void createOrder(OrderRequest request) {
        orderRepository.save(order);
        orderOutboxRepository.save(outboxEvent);
    }

Both writes happen in the same database transaction, so they either both commit or both roll back.
Outbox Table Schema:
{id, aggregate_type, event_type, aggregate_id, payload, created_at, published, published_at}

How do we then make sure that the event is processed later, we have a couple of ways:
i) Polling
A typical poller looks like:
    @Component
    public class OrderPoller {
        @Autowired
        private OutboxRepository outboxRepository;
        @Autowired
        private KafkaTemplate<String, String> kafkaTemplate;
        @Value("${outbox.polling.batch-size}")
        private int batchSize;

        @Scheduled(fixedRateString = "${outbox.polling.interval-ms}")
        public void pollAndPublish() {
            List<OutboxEvent> events =
                    outboxRepository.findUnpublishedEvents(batchSize);
            // query added in findUnpublishedEvents
            // SELECT * FROM outbox_events WHERE published = false ORDER BY created_at ASC LIMIT :batchSize
            if (events.isEmpty()) {
                return;
            }
            for (OutboxEvent event : events) {
                try {
                    kafkaTemplate.send(
                            event.getAggregateType(),
                            event.getAggregateId(),
                            event.getPayload()
                    ).get();
                    event.setPublished(true);
                    event.setPublishedAt(Instant.now());
                    outboxRepository.save(event);
                } catch (Exception e) {
                    // Stop processing this batch after a failure. Later events should not overtake the failed event when ordering is required.
                    break;
                }
            }
        }
    }

Important:
- Wait for the Kafka send result before marking the event as published.
- If Kafka stores the record but the acknowledgment is lost, the poller may retry and publish a duplicate.
- Consumers should be idempotent, or duplicate handling must be implemented.
- Marking an event as published must be committed to the DB. A crash between Kafka publication and the DB update can cause a duplicate on retry.

Issues with polling:
- Multi-instance handling: if three service instances poll simultaneously, they may select overlapping rows unless rows are claimed/locked correctly.
- Use a transaction and a query such as `SELECT ... FOR UPDATE SKIP LOCKED` to allow workers to claim different rows. The locks must remain valid while the rows are claimed or processed; do not hold long DB transactions open while waiting on Kafka without considering the impact.
- Ordering: parallel workers or multiple batches can publish later events before earlier ones. Ordering requirements may need per-aggregate sequencing or partitioning.
- Polling delay: events are published only when a poll runs.
- Constant DB checks even when no events are available.
- Published rows need a cleanup/retention strategy.
- Duplicate publication is possible if the process crashes after Kafka accepts an event but before the DB marks it as published.

ii) CDC (Change Data Capture):
Don't repeatedly ask the database for changes; capture changes as they happen. Use a CDC tool such as Debezium to capture committed changes to the outbox table from the database transaction log and publish them to Kafka.

Core technique:
During Master-Slave replication, the database can send transaction-log changes from the master to the slave. Debezium uses a similar underlying mechanism. It connects to the database and reads changes from its transaction log using the database's replication protocol. For example, with Postgres, Debezium reads changes from the Write-Ahead Log (WAL) through logical replication.

Advantages:
- No frequent polling queries against the outbox table.
- Reads committed database changes from the transaction log.
- Lower publication latency than periodic polling, depending on configuration.
- The application does not need to mark each event as published; retention and cleanup can be managed separately.

CDC still requires handling duplicate delivery and ordering requirements appropriately.
